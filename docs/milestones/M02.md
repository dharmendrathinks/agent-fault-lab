# M02 — Your first tool-using agent

The first genuine local run is now recorded in
[M02 live smoke test](M02-live-smoke.md), including the actual task ID, independent
database check, and an observed output-format limitation.

## The one idea to learn

The model does not execute Python or write to SQLite. It sends a structured
request such as `create_task` with `{"title": "Review the invoice"}`. Our code
checks that request, calls the ordinary function from M01, and sends back its
result. The model can request another tool or give its final answer.

That repeated conversation is the **agent loop**. There is no agent framework
and no need to expose or interpret hidden model reasoning.

## Read these files in order

1. `src/agent_fault_lab/model.py`: messages, tool requests, settings, and the small
   `ModelClient.complete(...)` interface.
2. `src/agent_fault_lab/tools.py`: the two advertised tools and strict arguments.
3. `src/agent_fault_lab/agent.py`: the sequential loop and stopping rules.
4. `src/agent_fault_lab/scripted.py`: programmed responses used to test the loop.
5. `src/agent_fault_lab/ollama_adapter.py`: translation to and from the local model.
6. `src/agent_fault_lab/trace.py`: the basic saved event record.
7. `src/agent_fault_lab/cli.py`: explicit offline demo, prerequisite check, and live run.

The M01 storage file is unchanged. It neither imports Ollama nor knows whether a
human, a scripted test, or a real agent requested an operation.

## Walk through it without a model

```sh
make agent-demo
```

This uses a **scripted test client, not AI**. The tool call is programmed, but its
SQLite write and returned identifier are real. A unique directory is retained
under `runs/`, ignored by Git. The command prints its exact path.

Open the trace in that directory. A normal scripted run contains these events:

| Event | What actually happened |
|---|---|
| `run_started` | Recorded the request, prompt, tool schemas, and limits |
| `model_requested` | Asked the selected client for its next response |
| `model_returned` | Recorded its content and requested tool calls |
| `tool_requested` | Recorded which allowed function is about to be attempted |
| `tool_returned` | Recorded the result, rejection, or storage error |
| `model_requested` | Sent the conversation, including the result, to the client |
| `model_returned` | Received a response with no more tool requests |
| `run_stopped` | Recorded the loop's stopping reason and counts |

This table describes the event contract; it is not fabricated terminal output.
See your actual JSONL file for generated identifiers, timings, and outcomes.

Multiple tool calls are executed in the order returned. Each gets a local ID such
as `m1-t1` or `m1-t2`, used to match requests and results in the trace. The pinned
Ollama SDK uses tool names and message order on the wire, not these local IDs.
A future provider with native call IDs will need its own mapping and contract tests.

## Validation at two boundaries

M01 validates values when ordinary functions are called. M02 additionally validates
the complete argument object returned by the model using strict Pydantic models:

- Missing fields, wrong types, blank strings, and extra fields are rejected.
- Valid titles retain their exact whitespace and punctuation.
- An unknown tool never reaches a Python function.
- The error becomes a tool response the model can react to on its next turn.
- Storage errors are reported as errors, not successful task creation.

Tool schemas advertise the expected shape; they do not enforce it. The pinned SDK
normalizes schemas, and model output is untrusted regardless. Actual enforcement
is in `execute_tool`. See [Pydantic strict validation](https://pydantic.dev/docs/validation/latest/concepts/strict_mode/).

## Local setup

The current baseline is `qwen3:4b-instruct-2507-q4_K_M`. The original M02 baseline
was `qwen3:4b`; its alias resolved to a thinking-only checkpoint and was explicitly
replaced during M04 on 2026-09-07. The historical M02 evidence is unchanged.
See [the diagnosis](M04-qwen-diagnosis.md). Tests and commands never download models
implicitly.

On another machine, an explicit one-time download is:

```sh
OLLAMA_HOST=http://127.0.0.1:11434 ollama pull qwen3:4b-instruct-2507-q4_K_M
```

Configure the **running daemon**, not just the Python client, for local-only mode.
Ollama documents `disable_ollama_cloud: true` in its server configuration, or the
`OLLAMA_NO_CLOUD=1` environment variable when starting the daemon; it requires a
restart. Preserve other settings and do not restart while another job needs it.
See [Ollama's official local-only instructions](https://docs.ollama.com/faq#how-do-i-disable-ollama-cloud-features).

For a manually managed daemon, after explicitly quitting/stopping any existing
Ollama instance, start it in a separate terminal:

```sh
OLLAMA_NO_CLOUD=1 ollama serve
```

Setting that variable only on `aflab run` does not reconfigure an existing daemon.
Then, from the project directory:

```sh
make doctor
uv run --offline --no-sync aflab run
```

`doctor` reads metadata, not prompts, and performs no inference. The local
`/api/status` response was observed on Ollama 0.33.2; it is not assumed to be a
stable endpoint on every older version. If it is missing or malformed, the check
fails closed and needs explicit setup investigation. There is no unsafe fallback.

The adapter also fixes the host to `127.0.0.1`, disables HTTP redirects and ambient
proxies, does not forward an environment API key, requires an installed model,
and rejects remote or mismatched checkpoint metadata. The approved checkpoint is
Qwen3-4B-Instruct-2507; generic `thinking` capability flags do not verify its mode.
These checks trust the local daemon; they are
not an operating-system network sandbox or a security certification.

The actual API integration follows the [official tool-calling conversation](https://docs.ollama.com/capabilities/tool-calling)
and [official Python client](https://github.com/ollama/ollama-python). Socket-free
HTTP contract tests exercise the installed client, but only a genuine live run
can demonstrate the local model completing this task.

## Inspect actual state after a live run

Read the returned run's `trace.jsonl` and `result.json`. Then open its database
independently, without calling the agent's `get_task` tool. Replace the example
path below with the exact path printed by your run:

```sh
sqlite3 -readonly runs/YOUR-RUN-DIRECTORY/tasks.sqlite3 'SELECT id, title FROM tasks;'
```

For the happy path, check that exactly one row exists, that its title is exactly
`Review the invoice`, and that any ID in the final answer matches that row.
Do not infer these facts from the word "Done". This is manual inspection in M02;
the reusable independent evaluator is M03.

## Stopping and evidence boundaries

| Loop status | Meaning |
|---|---|
| `finished` | Nonblank final response with no more tool requests; not a task grade |
| `model_limit` | Six model requests used, or a lower configured limit |
| `tool_limit` | A tool request exceeded the budget; that call was not executed |
| `provider_error` | A prerequisite/model request failed; no automatic retry |
| `protocol_error` | Empty or output-truncated model response |

Rejected calls consume the six-call tool budget; `tool_executions` separately
counts entry into real Python functions, including ones that raised storage errors.
Calling creation repeatedly still creates multiple tasks. No idempotency safeguard
is secretly added to this milestone.

The 60-second setting is an HTTP timeout, not a hard total runtime deadline or
proof that server computation stopped. Metadata reads have separate five-second
timeouts. Stronger cancellation experiments remain M08.

Each recorded line is flushed, but the trace is not transactional with SQLite
and not guaranteed durable under power loss. A disk error after a committed write
can leave incomplete evidence. Unexpected application errors are harness errors,
not scored as model behavior. Crash recovery remains M09.

Provider-reported token counts and durations are saved when available; missing
values remain absent, not zero. Ollama durations are in nanoseconds. Local elapsed
event timings use seconds and are not interchangeable with provider timings.
The manifest records model digest, daemon/package versions, and requested settings;
it cannot attest to all internal daemon behavior. Temperature zero is not a
determinism guarantee. No structured-output grammar is imposed yet.

CLI exit 0 means an experimental result was saved, even for a limit or protocol
outcome; it does not mean task success. Provider/setup/harness errors return 2;
keyboard interruption returns 130. Partial artifacts remain available when possible.

## Learning checkpoint before M03

Explain these using one actual trace:

1. Who chooses a tool, and who executes it?
2. What does the model receive after the tool returns?
3. How do two calls to the same tool keep their results in order?
4. Why can `finished` coexist with an empty database?
5. Which evidence came from a real model, and which came from the scripted client?
