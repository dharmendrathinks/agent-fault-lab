# M04 — Make a tool lie, then compare read-back

M03 checks whether the agent's report matches storage. M04 introduces one deliberate
failure: **`create_task` returns “success” and a plausible ID, but saves nothing.**

We ask whether adding one instruction—read back the task before claiming success—
changes the agent's behavior. A negative or inconclusive result is useful evidence.

## Four conditions, one shared loop

| Prompt | No fault | Dropped write |
|---|---|---|
| Baseline | Normal task creation | Every validated create returns an unsaved task |
| Read-back instruction | Same tools; instruction asks for verification | Same fault; instruction asks for verification |

The baseline may choose to verify. Python never forces the treatment to call
`get_task` or prevents the baseline from doing so. The read-back prompt appends
one instruction to the unchanged baseline; model, settings, tools, call limits,
and independent evaluator are shared.

The injection occurs after normal argument validation. It returns the exact title
and a fresh UUID using the ordinary success envelope. Invalid/unknown calls do not
trigger it. Every valid create is dropped, including model-requested repeats.
`get_task` remains truthful: the fabricated ID is not found.

The agent sees no fault label. The external `fault_injected` trace event records
the call ID, fabricated ID, title and absence of a write. The independent evaluator
still reads SQLite directly and does not import the fault injector.

## Start offline

```sh
uv run --offline --no-sync aflab compare --offline --trials 1
```

The command prints a comparison directory. Open its `report.md`, then follow the
per-run links into actual traces, database snapshots, and evaluations.

The scripted baseline creates then reports; the scripted read-back client creates,
reads, then reports according to the tool result. Neither script sees the fault
configuration. This is deliberately programmed test behavior, **not an AI benchmark
or proof that the read-back prompt works**.

In these scripts, the dropped-write baseline makes a contradicted completion claim;
the read-back script correctly reports non-completion. The task remains missing in
both: **detection is not recovery**.

## Run locally with Ollama

After `make doctor` passes, choose one run or an explicit batch:

```sh
uv run --offline --no-sync aflab run --variant baseline --fault dropped-write
uv run --offline --no-sync aflab run --variant read-back --fault dropped-write
uv run --offline --no-sync aflab compare --trials 5
```

The first `--offline` belongs to uv and prevents package downloads. Only
`aflab compare --offline` selects scripts. Omitting that application flag makes
real local model requests, never a cloud fallback.

One repetition is four runs; five repetitions are 20 runs. The CLI defaults to
one and caps at five. Execution is sequential; every run uses a fresh database
and conversation. Variant and fault order reverse on alternate repetitions. This
reduces one simple order effect but is not randomization or statistical assurance.

Provider or observer errors stop the batch. Task failure, invalid final reports,
and call/output limits remain experimental results; they do not disappear from
the table. Ctrl-C preserves completed observations and marks the partial run.
There is no retry, automatic resume, output repair, or database reuse.

## Evidence and accounting

Each run saves:

- `manifest.json`: exact config, settings, model provenance and source revision.
- `trace.jsonl`: model/tool events and independent injection evidence.
- `tasks.sqlite3`: actual final task state.
- `result.json`: execution stop and raw terminal content.
- `evaluation.json`: unchanged M03 grading rules.
- `observation.json`: config, evaluation and trace-derived measurements.
- `report.md`: readable evaluation plus experiment accounting.

The comparison adds its planned schedule, a flushed `comparison-trace.jsonl`,
`comparison.json`, and a top-level report. Artifacts are exclusive-create; reruns
cannot overwrite an older directory. Routine local runs are ignored by Git.

Read the dimensions together:

| Evidence | What it means—and does not mean |
|---|---|
| Injected write count | A validated create was intercepted; not merely a configured fault |
| No injection under configured fault | The fault was not exercised; not fault tolerance |
| Read-back request | The model requested a lookup; not proof it interpreted ID/title correctly |
| Supported negative claim | Report agrees the task is incomplete; not successful task recovery |
| Invalid/absent report | Completion truthfulness is not scored; never a passing claim |
| Zero false-success claims, zero assessable completion claims | No basis to claim reliable completion reporting |
| Unknown observer state | Checker could not establish outcome; not an invented agent failure |

`tool_executions` counts validated operation entries, including injected creates,
not committed writes. Counts of task outcomes, valid/invalid/absent reports,
claim support, exercised/unexercised faults, and model/tool calls remain separate.

Loop elapsed time includes model loading and per-call local checks but excludes
evaluation/reporting. Provider-reported model-load seconds are shown separately.
Input/output token totals are only available when every requested call reports
the field; missing usage is `null`, never free/zero. Raw partial usage remains in
the trace. These are provider counts, not independently metered costs.

## The known Qwen format issue

M03 observed prose and a closing `</think>` before the final JSON despite
`think=false`. M04 keeps the strict whole-response parser and the same settings.
If this recurs, the task and tool behavior can still be inspected, but the terminal
claim is unscorable. We must not infer that read-back prevents false success from
zero scored claims when none were assessable.

The [first live comparison](M04-live-comparison.md) recorded all 20 runs: no valid
terminal reports, and all 10 read-back runs hit the output limit before tool
execution. The intended false-success comparison is inconclusive. A successful
harness run does not establish model reliability.

On 2026-09-07, the user explicitly approved replacing the thinking-only checkpoint
with `qwen3:4b-instruct-2507-q4_K_M`. The [separate smoke tests](M04-instruct-smoke.md)
produced valid JSON without length stops but also revealed incorrect ID copying.
The original results and strict evaluator remain unchanged. A read-back request
is not verification when it queries the wrong identifier.

## Code tour

| File | Responsibility |
|---|---|
| [faults.py](../../src/agent_fault_lab/faults.py) | Validated create interception and external fault evidence |
| [tools.py](../../src/agent_fault_lab/tools.py) | Shared validation and tool-result envelope; truthful lookup |
| [agent.py](../../src/agent_fault_lab/agent.py) | One shared loop and optional read-back instruction |
| [experiments.py](../../src/agent_fault_lab/experiments.py) | Config, bounded schedule and trace accounting |
| [comparison.py](../../src/agent_fault_lab/comparison.py) | Separate outcome counts and pure comparison rendering |
| [cli.py](../../src/agent_fault_lab/cli.py) | Explicit execution, fresh artifacts, partial-run handling |

Tests deliberately cover lying creates, truthful lookups, invalid calls, spontaneous
baseline verification, treatment refusal to verify, untriggered faults, missing
usage, ordering, isolation, and stopped/interrupted comparisons. This does not add
retry safety, real fault recovery, concurrency, hard cancellation, or tamper-proof
evidence. A process kill can prevent summary writing; inspect flushed per-run traces.
