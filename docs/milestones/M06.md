# M06 — Tool contracts and malformed data

M06 adds response validation to the existing one-task experiment. It is included
in v0.2.0; the v0.1.0 tag preserves the original experiment.

## Three separate checks

1. **Syntax:** is the entire response valid JSON without duplicate keys or
   non-finite numbers? No extraction or repair is performed.
2. **Schema:** does the response contain exactly the supported, strictly typed
   fields, with consistent success/value/error states?
3. **Request consistency:** does a create response preserve the requested title,
   and does a lookup return the requested identifier?

None proves a write occurred. A fabricated task can pass all three checks. The
independent evaluator still reads actual SQLite rows through its own SQL path.
Conversely, a correct write can be followed by a malformed response. Rejecting
that response does not roll the write back or mean the task is missing.

## Try the offline experiment

From the locked project environment:

```sh
uv run --offline --no-sync aflab reliability list
uv run --offline --no-sync aflab reliability compare wrong-create-title --offline
uv run --offline --no-sync aflab reliability run malformed-json --policy validated --offline
```

The comparison creates two fresh databases and reports. Add `--trials 2` to
repeat the pair with policy order reversed. Trials are limited to 1–5. An explicit
`--output` must name a new directory whose parent exists.

Both policies validate arguments before execution. `pass-through` delivers the
raw response unchanged; `validated` delivers valid bytes unchanged or replaces an
invalid response with an ordinary `invalid_result` error. No automatic retry or
forced live read-back sequence is added.

The **same scripted client** is used in every offline cell. It creates, then reads
the returned ID, then claims completion from a success-shaped lookup. If it cannot
extract an ID, it reports uncertainty. It deliberately does not compare response
fields against its request. This is programmed test behavior, not a model result.

For `wrong-create-title`, the pass-through script can read back the correctly
stored task and finish, whereas validation returns an error after the task was
already committed and the script reports uncertainty. That is not evidence that
validation improved task completion.

## Supported cases

| Case | Injection boundary |
|---|---|
| `healthy` | No injected fault |
| `malformed-json` | Truncate the create response after the committed write |
| `duplicate-keys` | Add a conflicting duplicate JSON field |
| `non-finite` | Replace the schema version with a non-finite JSON value |
| `missing-field` | Remove a required envelope field |
| `extra-field` | Add an unsupported envelope field |
| `wrong-type` | Replace the boolean success value with a string |
| `unsupported-version` | Return envelope version 2 to the version 1 consumer |
| `wrong-create-title` | Alter only the create response title |
| `wrong-get-id` | Alter only a successful lookup's returned identifier |
| `dropped-write` | Existing M04 dropped-write mechanism; return a plausible task |

Response faults apply to each successful, task-valued eligible call. Lookup
not-found and tool errors remain truthful. `wrong-get-id` targets lookups; other
response faults target creates. Invalid input never exercises a fault. The model
may not call the eligible tool; reports include unexercised faults explicitly.

## Response and evidence contracts

The version 1 model-facing envelope requires all four fields, including nulls:

```json
{"schema_version":1,"ok":true,"value":{"id":"example-id","title":"Review the invoice"},"error":null}
```

Success has no error. Failed operations have a null value and an error with `code`
and `message`. A successful create must contain a task; a successful lookup may
contain null. IDs and titles are nonblank strings preserved exactly. A get result
is correlated by ID; its title cannot be verified against storage by the response
validator. Error categories are `invalid_arguments`, `unknown_tool`, `storage_error`,
and `invalid_result`. Execution counters and fault names are never envelope fields.

Run manifests use schema 4 and identify M06. The independent evaluation remains
schema 1 with evaluator `m03-v1`. New observations use artifact `reliability-run`,
schema 2; comparisons use artifact `reliability-comparison`, schema 2. These are
separate from legacy M04 observation/comparison schema 1. The initial M06 smoke
used reliability schema 1; those artifacts remain readable and unchanged.

`response_captured` trace events store exact raw bytes as base64. `contract_checked`
records valid/syntax/schema/request results; `contract_unchecked` records delivery
without validation. Fault events stay in external evidence. `tool_returned` records
delivered content with separate execution accounting.

Contract counts include valid, syntax errors, schema errors, request errors,
unchecked responses, and fault activations. Existing usage metrics remain
available; `injected_writes` counts the dropped-write mechanism specifically,
while `contracts.fault_activations` includes response faults too. Schema 2's
`metrics.fault_exercised` includes every activated fault. Initial M06 schema 1
inherited a dropped-write-only flag; use its contract counts for response faults.
Missing model usage stays null. Logical calls and entered operations remain distinct.

Use `aflab report RUN_DIRECTORY --check` for read-only presentation checks, or
omit `--check` to regenerate Markdown. Regeneration uses saved JSON only, does
not contact Ollama or inspect SQLite, and does not authenticate evidence.
Ambiguous, mismatched or unsupported saved evidence fails before report replacement.

## Focused live check

After offline verification, inspect `aflab doctor` and the installed checkpoint
metadata/digest. Use the approved local Instruct checkpoint and existing baseline
prompt/settings. The planned smoke is four runs:

```sh
uv run --offline --no-sync aflab reliability compare healthy --live
uv run --offline --no-sync aflab reliability compare wrong-create-title --live
```

`uv --offline` prevents dependency fetching; the explicit `aflab --live` mode still
performs local Ollama inference. It is not part of the default test suite.
Record every result, including invalid claims, wrong IDs and unexercised faults.
Do not rerun until favorable. See `PROGRESS.md` for actual verification and live
evidence status; this recipe alone is not evidence that inference ran.

The first four-run smoke is now recorded in [M06 live findings](M06-live-smoke.md),
including the wrong-ID claims, invalid final response, and accounting correction.
