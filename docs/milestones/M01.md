# M01 — Tools are ordinary functions

## The question

Before a model can create a task, what does the application need to do reliably?

It needs to accept a title, save it, and retrieve it by identifier. M01 implements
that operation without AI so later experiments have a simple, inspectable baseline.

## Read the implementation in this order

1. `Task`: a frozen data object containing `id` and `title`.
2. `TaskStore.create_task`: input validation, identifier creation, SQL insertion,
   commit, then return.
3. `TaskStore.get_task`: a parameterized lookup and an explicit not-found result.
4. `TaskStore._connection`: transaction completion and connection cleanup.

The source is `src/agent_fault_lab/tasks.py`; tests are in `tests/test_tasks.py`.

## What actually happens during a create

The caller supplies a title. The function rejects invalid input before attempting
an insert, assigns an identifier, and inserts the identifier and unchanged title
into SQLite. Leaving the transaction block commits the write. Only then does the
function return the `Task` object.

If the insert or commit fails, Python raises an exception before reaching the
return statement. There is no invented success response or swallowed storage error.

`get_task` opens a separate connection. It does not look up the object previously
returned from `create_task`. Reopening the store therefore exercises real persisted
data rather than an in-memory cache.

SQLite's connection context manager handles commit/rollback, but does not close
the connection. The implementation uses `closing()` for that separate job.
[Python SQLite documentation](https://docs.python.org/3.12/library/sqlite3.html#how-to-use-the-connection-context-manager)

## Run and inspect

```sh
make demo
make test
```

The demonstration uses a unique temporary directory and removes only that temporary
data when it finishes. Its UUID and temporary path change between executions; the
saved title and operation semantics should not.

The tests cover exact title preservation, invalid inputs, unknown identifiers,
reopening, isolated databases, parameterized SQL, and rejected inserts. A read-only
connection in the tests checks committed rows directly.

The rejected-insert test installs a trigger only in its disposable test database.
It verifies transaction error behavior; this is not yet an agent fault-injection
framework or an AI evaluation.

## Boundaries worth noticing

- Two creates with the same title produce two tasks. No duplicate prevention exists.
- `None` means a valid lookup found no matching task. A storage failure raises.
- Blank strings are invalid, but surrounding spaces on a meaningful title survive.
- Every operation is file-backed and uses a short-lived connection. No pooled
  connections, asynchronous execution, retries, or concurrency claims are present.
- A passing storage test says nothing about whether a model will choose the right
  tool or report its result honestly.

## Your learning checkpoint

Explain where the write commits, why the return statement comes afterward, and why
an independently read database row is stronger evidence than a returned object.
Then explain what two identical calls do today and why automatic retries might
become a problem later.

Stop here until this behavior is clear. M02 will let a local model request these
functions; it will not replace the storage implementation.
