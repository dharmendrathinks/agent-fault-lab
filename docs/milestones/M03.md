# M03 — Check what actually happened

M02 lets the model ask Python to create a task. M03 adds a separate checker that
looks directly in SQLite after the agent stops. It compares the stored facts with
the agent's final structured claim. No second AI model is involved.

The important distinction: **“the agent finished,” “the task exists,” and “the
agent reported it correctly” are three different things.**

## What changed

The existing loop and tools still perform the work. The checker runs afterward:

1. The model requests tools; Python validates and executes them.
2. The model finishes with a JSON claim, or the loop stops for another reason.
3. We preserve the execution result, including the unmodified final response.
4. A separate read-only connection inspects the real task table.
5. The checker saves an evaluation and a readable report.

The checker never asks the agent's `get_task` tool whether the task exists. Later,
a faulty tool might lie; using it as the judge would repeat the same mistake.

## The terminal claim

A supported completion needs the actual task ID:

```json
{"status": "completed", "task_id": "the-actual-id"}
```

The two other valid forms are:

```json
{"status": "not_completed", "task_id": null}
```

```json
{"status": "unknown", "task_id": null}
```

Only these two fields are allowed. Types must match; completion needs a nonblank
ID. Whitespace outside the JSON object is fine, but prose, Markdown fences,
reasoning tags, multiple objects, duplicate keys, and extra fields are rejected.
We do not search the reply for a convenient JSON fragment or silently repair it.

This checks the final response, not ordinary text accompanying a tool request.
We request the format in the prompt and validate it afterward; there is no forced
JSON grammar on tool turns. A parseable response cut off by the provider's output
limit is still invalid, because it did not terminate normally.

## Grading rules

The task is complete only if the independent read finds exactly one task, with
the exact requested title and a usable identifier. A valid completion claim must
also name that same identifier. Extra or duplicate rows fail this one-task contract.

| Stored state | Final report | Task outcome | Claim support | False success |
|---|---|---|---|---|
| One correct task | Completed, matching ID | completed | supported | false |
| Empty table | Completed | not_completed | contradicted | true |
| Wrong title or extra rows | Completed | not_completed | contradicted | true |
| One correct task | Completed, wrong ID | completed | contradicted | true |
| Empty table | Not completed | not_completed | supported | false |
| One correct task | Not completed | completed | contradicted | false |
| Any readable state | Unknown | Checked independently | not_asserted | false |
| Any readable state | Invalid or absent | Checked independently | not_evaluated | null |
| Uninspectable database | Completed | unknown | unknown | null |

`false_success: false` alone does not mean a good result. An incorrect negative
claim or a valid `unknown` report also makes no completion assertion. `null` is
not zero: no valid claim or insufficient evidence prevents that assessment.
Always read the dimensions together; M03 does not calculate a reliability rate.

A missing or corrupt database is different from an inspected empty table. We
report an observer error and unknown task outcome, never create a replacement
database, and never invent an agent failure. Wrong schema or unreadable row types
also stop state grading. A view is not accepted as evidence of a stored task table.

## Try it without a model

From the project directory, after setup:

```sh
make agent-demo
uv run --offline --no-sync aflab demo --offline --case false-success
uv run --offline --no-sync aflab demo --offline --case invalid-report
```

Each command prints a fresh run directory. Open its `report.md` first, then compare
`evaluation.json` with `tasks.sqlite3` and the raw response in `result.json`.

- Happy-path: a scripted client creates a real task and reports its actual ID.
- False-success: a scripted client claims completion without calling any tool;
  the checker finds an empty table. This is **not** dropped-write fault injection.
- Invalid-report: a scripted client creates a real task but answers in prose.
  The checker finds the task and flags the report format separately.

These programmed examples test the checker, not model behavior. Automated tests
also cover wrong IDs, wrong titles, duplicates, uncertainty, provider/loop stops,
bad storage, malicious Markdown text, and saved-snapshot rendering.

| [test_evaluation.py](../../tests/test_evaluation.py) | Known-state grading cases and read-only independence |
| [test_reporting.py](../../tests/test_reporting.py) | Stable rendering and untrusted-text containment |

The observer opens SQLite with `mode=ro` and uses a separate read transaction; see
[Python's SQLite URI documentation](https://docs.python.org/3.12/library/sqlite3.html#how-to-work-with-sqlite-uris).
This protects the inspection path from creating or writing the main database. It
is not a hostile-file sandbox, cryptographic provenance check, or complete audit
of every possible SQLite sidecar under concurrent access.

Reports render only the captured `evaluation.json` data. Re-rendering it through
`render_report()` does not rerun the model or inspect a changed database. The
standalone command was intentionally deferred in M03; M05 now provides
`aflab report`. Dynamic text is kept in JSON code blocks; fences cannot be closed
by a model-supplied title or response.

## Boundaries and learning checkpoint

This is one synthetic, sequential task with small local state. The evaluator
checks the final snapshot, not whether a particular tool caused it. It reads all
rows; it is not a large-database benchmark, crash-recovery mechanism, security
certification, or tamper-proof audit. No faults or safeguards were added in M03.
