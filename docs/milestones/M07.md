# M07 — Retry and duplicate-effect safety

A missing reply can follow either no write or a committed write. Retrying helps
the first case, but can create a second task in the other case. An operation ID
lets storage recognize another delivery of the same logical action.

## Run the experiment

From a checkout with the locked local environment:

```sh
uv run --offline --no-sync aflab reliability list
uv run --offline --no-sync aflab reliability compare lost-reply-once --offline --include-control
uv run --offline --no-sync aflab reliability compare before-write-once --offline --include-control
uv run --offline --no-sync aflab reliability compare retry-healthy --offline --include-control
```

Each command prints a new comparison directory under ignored `runs/`. Open its
`report.md` and the child reports. These scripted examples exercise real SQLite
and independent evaluation, but do not measure model behavior.

| Case | Single attempt: rows | Unprotected retry: rows | Idempotent retry: rows |
|---|---:|---:|---:|
| Healthy | 1 | 1 | 1 |
| Fail once before write | 0 | 1 | 1 |
| Lose one reply after commit | 1 | 2 | 1 |

These counts describe the fixed script issuing one create. A model can request
additional creates. In the single-attempt lost-reply case, the task exists even
though the client received an error and the script reports unknown. Under an
unprotected retry, two rows violate the task's exactly-one-row requirement; a
completion claim is contradicted even if its returned ID exists.

Use `run CASE --policy POLICY --offline` for one cell. `compare` without
`--include-control` runs just the two retry policies. Alternate trials reverse
policy order. `--live` explicitly selects local inference after checkpoint
preflight. The six planned live smoke runs and limitations are recorded in
[M07-live-smoke.md](M07-live-smoke.md).

## What the ID protects

The executor assigns a UUID after validating a tool request. Both attempts of
that operation share it; each has a distinct attempt ID. Another model request
gets a new operation ID, even with the same title or reused model call identifier.
Equal arguments alone cannot distinguish a retry from an intentionally separate task.

Protected creation opens a SQLite write transaction before checking the operation
ledger. A new key inserts the task and its ledger record in the same transaction.
The method returns only after commit. A known key with the same exact title returns
the original task. A different title produces `operation_conflict` without mutation.
Spaces and Unicode remain unchanged. Ledger entries last as long as the database.

The guarantee is **at most one task effect per retained operation ID in this
database**. Delivery can still fail twice; the caller can remain uncertain. New
IDs can still create duplicates. This is not exactly-once delivery, protection
against repeated model intent, or durability beyond SQLite and its storage device.
External mutation of task/ledger tables is outside the append-only experiment.

## Retry admission and evidence

Both injected positions expose the identical delivery failure. The retry rule
does not inspect the injector's commit-position flag. Only delivery failure gets
one immediate retry; invalid arguments, malformed results, operation conflicts
and storage errors do not. Exhaustion returns an error with unknown storage
outcome, then the evaluator inspects the actual task table independently.

Trace events connect `operation_started`, `attempt_started`, `storage_entered`,
`storage_returned`, `attempt_failed`, `retry_scheduled`, and `attempt_succeeded`.
Raw returned bytes are base64 captured before contract validation. A lost reply
has no returned bytes; its storage receipt remains external evidence. Replay flags,
operation IDs and fault-position metadata never enter model-facing responses.

Logical calls, attempts, retries and storage entries are different counts. In a
protected lost-reply create there are two attempts and two storage entries, but one
task row and one replay. A later lookup adds a logical call and storage entry.
The final evaluator snapshot, terminal JSON validity and exact claimed task ID
remain separate from all these counts.

```sh
uv run --offline --no-sync aflab report runs/YOUR-COMPARISON --check

make package-check
```

Report regeneration reads saved JSON without opening SQLite or invoking a model.
Tests cover all nine cells, exact inputs, conflict, reopening, concurrent delivery,
insert and commit rollback, retry admission/exhaustion, partial runs and reports.
M07 has no delayed retries, tool deadlines, worker termination or process resume.

## Learning checkpoint

Review why a successful read of one returned ID cannot rule out a duplicate row;
why the operation record must commit with the task; and why two identical model
requests receive separate IDs. Technical checks and this review are separate.
M08 starts only after its own authorization.
