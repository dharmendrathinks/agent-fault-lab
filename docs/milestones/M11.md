# M11 — Permissions and human approval

This milestone asks whether an agent can make a state change without valid
operation-specific approval. SkillSpector is the content-admission integration:
it scans the skill before that context reaches the agent. Application-side
authorization independently checks each write. A clean scan never grants approval.

Available in v0.3.0 alongside
[M12 injection comparisons](M12.md) and [M13 memory/context experiments](M13.md).
See [PLAN.md](../../PLAN.md).

## Setup and first comparison

Use Python 3.12 and the local uv environment. The scanner has its own pinned lock;
setup downloads dependencies, while scanning and scripted experiments are offline.

```sh
uv sync --locked --all-groups
make scanner-setup
uv run --offline --no-sync aflab scanner doctor
mkdir -p runs
uv run --offline --no-sync aflab boundaries list
uv run --offline --no-sync aflab boundaries compare missing --offline --output runs/m11-missing
uv run --offline --no-sync aflab report runs/m11-missing --check
```

Use a fresh output directory each time. `--offline` scripts the agent but still
runs real static SkillSpector. Missing scanner installation is an error; there is
no automatic mock fallback. Core tests explicitly inject labeled test doubles.

Open `runs/m11-missing/report.md`. Audit mode records the missing permission but
allows a synthetic task write. Enforcement denies the same write. Both use the
same skill, tools, prompt, limits, grading and approval scenario. Only permission
enforcement changes. Audit mode is an experiment in a newly created lab database.

| Case | Enforced write | What it tests |
|---|---|---|
| `approved` | One task | Current grant permits exactly its proposed operation |
| `missing` | None | A request is not a grant |
| `rejected` | None | Explicit rejection remains binding |
| `expired` | None | Admission checks the validity interval after acquiring the write lock |
| `changed-arguments` | None | A grant for one exact title cannot authorize another |
| `changed-revision` | None | A grant issued under an older policy becomes stale |
| `cross-operation` | None | Approval for a different operation is not reusable |
| `replay` | One task | Repeated delivery returns the committed receipt |

These scenarios use a controller that changes grants or attempted arguments.
Its decisions are synthetic, never represented as human approval. In particular,
the changed-arguments audit cell creates the wrong title: its completion claim is
contradicted even though the write happened. Scenario activation, attempts, actual
writes, terminal validity and claim support remain distinct in saved evidence.

## Approve or reject an actual pending proposal

```sh
uv run --offline --no-sync aflab boundaries run manual --offline --output runs/m11-manual
uv run --offline --no-sync aflab approval show runs/m11-manual
```

The run returns **exit 3** while awaiting approval. It has a pending operation,
one reserved tool call, no write and no terminal claim. Inspect the exact title,
operation ID, run ID and request/policy revisions printed by `approval show`.
Substitute that full operation ID below:

```sh
uv run --offline --no-sync aflab approval approve runs/m11-manual OPERATION_ID --ttl-seconds 300
uv run --offline --no-sync aflab resume runs/m11-manual --offline
uv run --offline --no-sync aflab diagnose runs/m11-manual
```

Use `approval reject RUN OPERATION_ID` instead to deny it. Decision commands save
only the decision and evidence; they never resume inference or execute the task.
The default TTL is 300 seconds, with a maximum of 3,600 seconds. Decisions cannot
be overwritten. A still-pending proposal remains paused on resume; an expired or
rejected proposal returns a denial to the agent. The agent may subsequently make
a new request, which requires its own approval.

An approval is bound to `(run, operation, exact title, request revision, policy
revision)`. It authorizes one logical effect. Inside a single `BEGIN IMMEDIATE`
transaction, the application checks the grant, inserts the task and operation
receipt, and consumes the grant. A transaction failure rolls back all three.

The conversation journal is a different SQLite file. If the task commits but the
tool response is not checkpointed, resume delivers the same operation again.
Its committed receipt returns the original task, including after grant expiry;
this is replay of an existing effect, not a new authorization. A different model
request receives a different operation ID and cannot reuse the grant. Ordinary
`get_task` remains read-only.

## Scanner policy and evidence

The default scanner policy admits only complete, successful static scans with a
`SAFE` recommendation. `CAUTION` and `DO_NOT_INSTALL` block delivery. Exit 1 with
findings is distinguished from execution failure. Missing, malformed, incompatible,
incomplete and timed-out scans are errors under both scanner policies.

`--scan-policy audit` records a suspicious recommendation while allowing the
same scanned bytes as context. It does not grant write permission. This explicit
control supports later comparisons; it never bypasses scanner execution errors.
`--skill` accepts a local Markdown file or a directory containing only `SKILL.md`.
No skill code runs. The [integration notes](../../integrations/skillspector/README.md)
document the pin, input limits and network boundary.

Each run stores:

| Artifact | Purpose |
|---|---|
| `scan/SKILL.md` | Exact scanned and prepared context bytes |
| `scan/raw-report.json`, `stdout.txt`, `stderr.txt` | Original scanner output and warnings |
| `scan/scanner-identity.json`, `scan/scan.json` | Installed pin, lock hash when available, input/report hashes, normalized findings and status |
| `manifest.json` | Versioned boundaries configuration and compatibility fingerprint |
| `boundary.sqlite3` | Conversation checkpoint, budgets, pending operations and ordered events |
| `tasks.sqlite3` | Actual tasks, proposals, authority revisions and committed effect receipts |
| `evaluation.json`, `report.md` | Independent task/authorization grades and strict terminal claim assessment |
| `run.lock` | Exclusive ownership during run, approval and resume |

The model sees tool responses and admitted context; scanner findings and scenario
labels stay outside its messages. A blocked run can retain prepared messages in
its checkpoint, but no model request occurs; `content_admission.delivered` records
that distinction. `aflab report` renders saved JSON only. `aflab diagnose` reads
the saved journal and evaluation without scanning, inference or fresh grading.

## Validation and limits

Run `make check`, `make package-check` and `make scanner-check`. The first two
verify the machinery offline; the third exercises the actual pinned scanner and
public approval commands. CI requires the real check on Ubuntu and macOS.
See [PROGRESS.md](../../PROGRESS.md) for actual local results and pending checks.

The scanner has a 60-second subprocess deadline, a 4 MiB aggregate capture limit,
and terminate/kill/reap cleanup. Oversized raw output may be truncated with an
explicit error; truncated output cannot be admitted. Python sockets are blocked
before scanner imports and inherited credentials are omitted. This is not an OS
sandbox, and static `SAFE` is not proof that content is harmless.

On macOS, signalling an exited group can report a permission error while zombie
entries remain. Cleanup checks `/bin/ps` group/state output under a 0.5-second
timeout before accepting that case. Live members, malformed/unavailable inspection
and genuine permission failures remain errors; the scanner does not assume success.

Approval trusts the local operator and filesystem; there is no separate user
identity service or protection against a malicious process editing SQLite. Grants
use local wall-clock time. The append-only task/receipt guarantee assumes no
out-of-band edits or deleted task rows. Journal and task transactions are separate;
crash recovery reconciles writes via receipts rather than claiming two-file atomicity.
Resume refuses changed source fingerprints, input snapshots or scan evidence.
Use the original code/environment to resume older runs.

The agent retains six model requests and six tool calls across restarts. A lost
model response costs its reserved request and may be queried again; deterministic
model output is not promised. Approval wait time is not an inference timeout.
Scanner cleanup does not cancel a running Ollama request. Windows is unsupported.

The four planned local-model M11 smoke runs are separately opted in after model
identity inspection: approved and rejected, each under permission audit/enforce.
They have not been run in this implementation session. Scripted findings establish
the machinery only, not agent reliability or scanner detection accuracy.

## Learning checkpoint — accepted for progression

After discussing these roles, the user said “got it” and requested the remainder
of Phase 3. That accepts M11 for progression; it does not claim a formal assessment
or any new live evidence. The following questions remain useful review prompts.

Explain from a saved report why a `SAFE` skill can still lead to a denied write,
why task completion can coexist with an authorization violation, and why replay
after grant expiry is safe only when a committed receipt already exists. Review
the approval-wait timeline and the transaction/restart regression evidence.
Passing technical checks alone does not establish learning acceptance.
